## 2. 技术选型

### 2.1 选型表

| 层 | 选型 | 依据 |
|---|---|---|
| 生成模型 | **Ollama + `qwen3:4b`（2.5GB）→ `qwen3:8b`（5.2GB, Q4_K_M, Apache-2.0）** | 装完即用，Metal 加速，HTTP API 与语言无关；M1 16GB 上 8B 常驻约 8GB 内存，先用 4b |
| 向量模型 | **fastembed + `Qwen/Qwen3-Embedding-0.6B-Q`**（1024 维，ONNX int8，**不需 PyTorch**） | 中文强 + 1024 维 + 体积可控；纯 onnxruntime，装机 ~150MB。**注意 fastembed 0.9.1 不支持 bge-m3**，详见 §8.2 |
| 重排模型 | **fastembed `TextCrossEncoder` + `BAAI/bge-reranker-v2-m3-int8`** | RAG 质量最大单一杠杆；同 ONNX 无需 torch；选 int8 版是因为 fp16 要 2.27GB |
| 向量库 | **LanceDB（嵌入式，无服务无 Docker）** | 官方支持向量 + 全文混合与 RRF；本方案**只拿它当向量仓库 + 元数据过滤**，融合算法自己写 |
| 关键词索引 | **jieba + bm25s（自建，落盘）** | **中文必须分词**；LanceDB 内置 FTS 是英文分词器，中文直接用会崩 |
| 后端 | **Python 3.13 + uv + FastAPI** | AI 生态最通用；uv 装依赖快 |
| 前端 | **Vue 3 + Vite + Pinia** | 沿用既有个人项目的默认栈 |
| 流式 | **SSE** | 单向够用，比 WebSocket 简单一个数量级 |

### 2.2 被否决方案对照表

| 方案 | 否决原因 |
|---|---|
| LangChain / LlamaIndex | 黑盒；既有项目一次没用过；自己实现才学得到、才好调参 |
| 云端 API（Claude / 千问 / DeepSeek / MiniMax） | 与「自己的 AI」目标直接冲突；也断网即废 |
| Chroma / Milvus / Qdrant 服务 | 16GB 内存下多常驻进程不划算；Milvus 是工作项目的方案，个人玩具用不上 |
| Postgres + pgvector | 要起 Postgres 进程；工作项目在用但那是另一回事 |
| v1 就上 LoRA 微调 | **RAG 解「知识」，微调解「行为 / 风格」，顺序反了**；先调通 RAG，微调留 M5 |
| 内置 OCR | 中文 PDF 文本层质量参差，自研成本高；v1 明确提示用户 |
| PyMuPDF（AGPL） | 个人项目无碍，但需标注：日后若要商用，换 pdfplumber（MIT） |

### 3.2 数据流

```
上传 / URL / 本地路径
  → loader：各格式统一转 Markdown（保留标题层级）
  → chunker：结构感知切块 + metadata
  → embedder：Qwen3-Embedding-0.6B-Q → 1024 维（查询带指令前缀）
  → store：向量入 LanceDB(HNSW)；jieba 切词入 bm25s 索引（落盘）

查询
  → 稠密 top-50（LanceDB）∥ 关键词 top-50（bm25s）
  → 自写 RRF 融合（K=60）→ top-20
  → 邻居扩展（命中块 ±1）
  → reranker 精排 → top-5 → 每块裁到 800 字
  → prompt 组装（带 [n] 编号与来源标签）
  → Ollama /api/chat stream
  → SSE 推前端：delta 文本 + citation 引用 + done
```

### 3.3 关键数据结构

#### Chunk metadata 字段表

| 字段 | 类型 | 说明 |
|---|---|---|
| `chunk_id` | str | `f"{doc_id}:{chunk_idx}"`，全局唯一主键 |
| `doc_id` | str | `sha1(source_path + mtime)[:16]`，同一文件改动即换 ID |
| `source_path` | str | 原始路径或 URL |
| `source_type` | str | `md/txt/pdf/docx/xlsx/pptx/url` |

| `content` | str | 块正文（Markdown 片段） |
| `content_hash` | str | `sha1(content)`，跨文档去重 + 幂等更新 |

## 4. RAG 六步实现细节

### 4.1 解析 `ingest/loader.py`

```python
def load(source: str, source_type: str) -> ParsedDoc:
    """统一入口。source 是本地路径或 URL。
    返回 ParsedDoc(title: str, markdown: str, meta: dict)
    """
```

| 类型 | 库 | 要点 |
|---|---|---|
| md/txt | 标准库 | 直读；md 保留原样，txt 按空行分段 |
| pdf | **PyMuPDF (fitz)** | 逐页 `page.get_text()`；记录页码映射。**检测到某页文本 <50 字符 → 标记 `needs_ocr=True`，不静默产出空块** |
| docx | **python-docx** | 按 `style.name` 判断 Heading 级别 → 转 `#`，正文段落转普通文本，表格转 md 表格 |
| xlsx | **openpyxl** | 每个 sheet → 一个 md 表格 + 表名作为 heading；空 sheet 跳过 |
| pptx | **python-pptx** | 每页 → `## 第N页 {标题}` + 各文本框内容（占位符跳过） |
| url | **httpx + trafilatura** | `trafilatura.extract()` 抽正文去广告；保留原 URL；失败降级用 BeautifulSoup 去标签 |

**统一约定**：所有格式转出的 Markdown **必须保留标题层级** —— 这是 [4.2](#42-分块-ingestchunkerpy) 结构感知分块的前提。

### 4.2 分块 `ingest/chunker.py`

```python
def chunk_markdown(md: str, source_meta: dict,
                   target_chars: int = 500,
                   overlap_chars: int = 80) -> list[Chunk]:
    """返回带 heading_path 的块列表。"""
```

**算法**

1. 正则扫标题：`^(#{1,6})\s+(.+)$` → 维护 `heading_path` 栈（进栈 push，出栈 pop 到同级）
2. 每个标题下的正文 = 一个 section
3. section 内按 `\n\n` 切段落；**代码块（``` 包裹）和表格（以 `|` 开头）整体不切**
4. 段落累积到 `target_chars` 就切一刀；切点优先落在 `。！？；` 或 `\n` 边界
5. 相邻块重叠 `overlap_chars`：下一块开头回溯上一块末尾 N 字（按句边界回退，不切断句子）

**参数取值与依据**

| 参数 | 值 | 依据 |
|---|---|---|
| `target_chars` | 500 | <300 字语义不完整（问答常需跨句）；>800 字超出嵌入模型 512-token 训练窗口，检索精度下降 |
| `overlap_chars` | 80 | 约 16%，够覆盖被切断的句子，又不至于让相邻块在召回时高度重复（重复会挤占 top-k 名额） |
| 切点优先级 | 句读 > 段落 > 硬切 | 保住句子完整性，直接影响生成时的可读性 |

### 4.3 向量化 `rag/embedder.py`

```python
class Embedder:
    def __init__(self, model_name: str = "Qwen/Qwen3-Embedding-0.6B-Q",
                 dim: int = 1024,
                 query_instruction: str = DEFAULT_QUERY_INSTRUCTION): ...
    def embed_documents(self, texts: list[str]) -> np.ndarray: ...   # (n, 1024) L2 归一化
    def embed_query(self, text: str) -> np.ndarray: ...            # (1024,)
```

- fastembed `TextEmbedding`，**batch=32**（16GB 机器上稳），模型缓存在 `~/.cache/fastembed`
- **查询必须加指令前缀**，文档不加 —— Qwen3-Embedding 的官方约定：
  `Instruct: {任务描述}\nQuery:{问题}`。不加会明显掉点。
  任务描述要跟实际用途对上（这里是「从个人知识库检索能回答问题的段落」，不是网页搜索），
  存在 `EMBED_QUERY_INSTRUCTION` 环境变量里，换模型时改这里即可
- 归一化后余弦相似度 = 点积，LanceDB 索引设 `metric="cosine"`

### 4.4 召回 `rag/retriever.py`

```python
class Retriever:
    def retrieve(self, query: str, top_k: int = 5) -> list[ScoredChunk]: ...
```

**融合算法自己写**（不用 LanceDB 内置 hybrid，原因见下）：

```
dense = vector_store.search(query_vec, limit=50)          # LanceDB
bm25  = bm25_index.search(jieba.lcut(query), limit=50)     # 自己的索引

RRF:  score(d) = 1/(60 + rank_dense(d)) + 1/(60 + rank_bm25(d))
      只出现在一路里的，另一路贡献 0
→ 取 top-20
→ 邻居扩展：对 top-20 每个命中，取同 doc_id 的 chunk_idx±1 加入候选（去重）
→ 交给 reranker 精排
```

**为什么不直接用 LanceDB 的 hybrid/RRF**：它的 FTS 走 Rust 倒排索引 + 英文分词器，中文分词不可控。我们把 LanceDB 降级为「纯向量仓库 + 元数据过滤」，BM25 用 jieba 自己做 —— 融合算法、分词策略都在自己手里，正好是「自己实现」的核心部分。

**参数依据**

| 参数 | 值 | 依据 |
|---|---|---|
| `RETRIEVE_TOP_N` | 50 | 召回阶段宁多勿漏；50 条在 CPU 上重排成本约 1~2s，可接受 |
| `RRF_K` | 60 | 业界通用值（LanceDB 官方默认也是 60） |
| 邻居扩展 | ±1 块 | 缓解「答案恰好被切断在两块之间」 |

### 4.5 重排 `rag/reranker.py`

```python
class Reranker:
    def __init__(self, model_name: str = "BAAI/bge-reranker-v2-m3-int8", enabled: bool = True): ...
    def rerank(self, query: str, chunks: list[Chunk]) -> list[ScoredChunk]: ...
```

- fastembed `TextCrossEncoder`，输入 `(query, chunk.content)` 对
- 取 top-5，每块 `content` 裁到 **800 字**（再长信息密度下降且挤占上下文）
- `RERANK_ENABLED=false` 时跳过 —— 既是磁盘 / 内存紧张时的降级开关，也是 A/B 评测的对照组

### 4.6 提示词 `rag/prompt.py`（全文）

```python
SYSTEM_PROMPT = """你是一个严谨的知识库问答助手。你只能依据【参考资料】中的内容回答问题。

规则：
1. 只使用【参考资料】中出现的信息，不要用自己的先验知识补充或推断。
2. 每条结论后面必须标注来源编号，格式如 [1] 或 [1][3]，编号对应参考资料前的 [n]。
3. 如果参考资料不足以回答，直接说"现有资料无法回答这个问题"，并说明还缺少什么信息。不要猜测、不要编造。
4. 用简体中文回答，简洁直接：先给结论，再给必要的展开。
5. 参考资料之间出现矛盾信息时，把矛盾点指出来，不要擅自选一个。
6. 不要复述问题，不要写"好的""根据参考资料"这类开场白。"""

USER_TEMPLATE = """【参考资料】
{context}

【问题】
{question}"""


def build_context(chunks: list[ScoredChunk]) -> str:
    """每块前加 [n] 编号 + 来源标签。"""
    parts = []
    for i, c in enumerate(chunks, start=1):
        src = c.source_path
        if c.heading_path:
            src += " > " + " > ".join(c.heading_path)
        if c.page is not None:
            src += f" 第{c.page}页"
        parts.append(f"[{i}] (来源：{src})\n{c.content}")
    return "\n\n".join(parts)
```

**生成参数**：`temperature=0.1`、`top_p=0.8` —— RAG 是「提取 + 改写」任务不是创作任务，低温度更忠于资料；`num_ctx` 设 8192 足够（实际用量 ≈ 5×800 字 + 问题）。

### 4.8 评测 `eval/`

**评测集 `qa.jsonl`（手写 20~50 条，这是「长期玩」的关键抓手）**

标注用「文件名 + 块序号」，**不要**硬编码 `chunk_id`：

```json
{"id":"q001","question":"生产环境必须设置哪两个环境变量？","answer":["DATABASE_URL","REDIS_URL"],"source_name":"部署手册.md","chunk_idxs":[1],"note":"考察事实型召回"}
```

为什么不用 `chunk_id`：它是 `{doc_id}:{chunk_idx}`，而 `doc_id` 由「路径 + mtime」哈希而来，
文档重新上传一次就变了，评测集当场失效。改用「文件名后缀 + 块序号」后，
只要分块参数没动，标注就一直有效（分块参数一改，块序号全变，标注要重做）。

标注流程：`uv run python -m app.eval.run --inspect` 会打印每题召回的块及其 `chunk_idx`，
把正确的那些填进 `chunk_idxs` 即可。

**指标**

| 指标 | 定义 | 用途 |
|---|---|---|
| Recall@k | 期望块出现在 top-k 结果中的比例，k=1/3/5/10 | 检索层质量 |
| MRR@k | 第一个期望块的倒数排名 | 排序质量 |
| 答案命中率 | 生成答案包含 answer 全部关键词（子串匹配） | 生成层质量 |
| 端到端正确率 | 命中且答案命中 | 综合 |

**量的是「最终进上下文的那批块」**：开了重排就按重排后的顺序算。
量 RRF 融合顺序的话，重排的贡献永远看不出来（重排的价值恰好是「把对的块顶到前面」）。

**运行**

```bash
uv run python -m app.eval.run --k 5             # 默认 qwen3:4b
uv run python -m app.eval.run --k 5 --no-rerank  # A/B：关掉重排对比
uv run python -m app.eval.run --inspect          # 打印召回块，人工标注用
uv run python -m app.eval.run --answer           # 额外跑生成层，算答案命中率
```

结果存 `eval/results/{timestamp}.json` 并保留历史（连同当时的分块大小、top-n、RRF K、模型名）→
每次改参数（分块大小、top-k、rerank 开关、提示词）都能量化对比，**不靠感觉**。

## 6. 风险与备选

| 风险 | 触发信号 | 对策 |
|---|---|---|
| **磁盘不足** | 磁盘 91% 已满 | Step 0 先清；`OLLAMA_MODELS` 指向外置盘；模型只留 4b |
| **内存吃紧** | swap 飙升、推理变慢 | 换 `qwen3:4b`；`RERANK_ENABLED=false`；`OLLAMA_MAX_LOADED_MODELS=1` |
| **中文 BM25 不分词** | 召回结果全是不相关块 | 已用 jieba；若效果仍差 → 加一路稀疏检索（SPLADE，fastembed 有支持）做第三路融合 |
| **PDF 无文本层 / 乱码** | 某页文本 <50 字符 | loader 检测后标记 `needs_ocr`，前端提示「该 PDF 需 OCR，v1 不支持」 |
| **Ollama 冷启动慢** | 首个请求 10s+ | `keep_alive="5m"` + `brew services start` 常驻 |
| **想换推理后端** | Ollama 满足不了 | `llm/ollama.py` 是唯一耦合点，换 llama.cpp server 只改这一个文件（两者都 OpenAI 兼容） |
| **模型不够好** | 评测分数上不去 | 先分清是检索问题还是生成问题（看 Recall@5）—— 检索差 → 加重排 / 调分块；检索好但答案差 → 换模型或调提示词 |

### 8.2 与原设计的偏差（**都带原因**）

| # | 原设计 | 实际做法 | 为什么 |
|---|---|---|---|
| 1 | PDF「某页文本 <50 字符就标 needs_ocr」 | **过半页面**文本稀薄才标，明细记在 `meta["low_text_pages"]` | 按字面实现的话，几乎每份 PDF 都会被标（封面、目录页、章节扉页都容易踩线），标记形同虚设 |
| 2 | SSE 事件顺序 `delta → citation → done` | `citation → delta → done` | 前端按事件类型渲染，引用先到能让来源在生成过程中就显示出来，而不是等答案出完 |
| 3 | BM25 索引「入库时增量更新」 | **语料增量、索引可重建**（bm25s 不支持增删改） | bm25s 只有 `index()` / `retrieve()`，删文档和改文档都得重建。几千个块的量级重建 1~3 秒，个人项目完全够用 |
| 4 | 向量库 `heading_path` 存 list | 存 **JSON 字符串** | LanceDB schema 里嵌 list 类型负担更重，JSON 字符串更好查（取值时用 `json.loads` 还原） |
| 5 | 重排器直接改 `chunk.score` | **不改原对象**，返回新对象 | 调试面板要同时看 RRF 分和重排分，被覆盖就看不到了 |
| 6 | 知识库为空时的问答行为 | 空库退化成直通对话；**非空但没召回到**才说「无法回答」 | 空库是「还没导入资料」，不是「资料不足」，两者要区分开，否则新用户以为坏了 |
| 7 | Python `>=3.13` | **锁 `>=3.13,<3.14`** + `server/.python-version` | onnxruntime 还没有 cp315 wheel，而 brew 会把默认 python3 升到 3.15 |
| 8 | 向量模型 `BAAI/bge-m3` | **`Qwen/Qwen3-Embedding-0.6B-Q`** | **fastembed 0.9.1 的模型列表里根本没有 bge-m3**（只有 bge-base-en / bge-small-zh 等）。Qwen3-Embedding-0.6B-Q 是列表里「中文强 + 1024 维（与原 schema 一致，不用改表）+ 1.1GB」的唯一最优解。代价：查询要加 `Instruct:…\nQuery:…` 前缀，否则掉点 |
| 9 | 重排模型 `BAAI/bge-reranker-v2-m3` | **`BAAI/bge-reranker-v2-m3-int8`** | fp16 版要 2.27GB，磁盘只剩 21GB 装不下也不划算；int8 版 0.57GB，RAG 场景质量损失几乎看不出来 |
| 10 | 模型从 huggingface.co 直接下 | **`HF_ENDPOINT=hf-mirror.com`** + 缓存放 `~/.cache/fastembed` | 直连 huggingface.co 会一直超时挂住；fastembed 默认把权重放系统临时目录，macOS 重启就清掉，1.7GB 得重下。两者都在 `app/hf_env.py` 里、于 import fastembed 之前设好 |
| 11 | 评测集标注写死 `chunk_ids` | **`source_name` + `chunk_idxs`** | `chunk_id` 里的 doc_id 由「路径 + mtime」哈希而来，文档重新上传就变，评测集当场失效。改用「文件名后缀 + 块序号」后重新入库也还对得上 |
| 12 | 评测指标量 RRF 融合顺序 | **量重排后的顺序** | 重排的价值就是「把对的块顶到前面」；量融合顺序的话，重排开不开指标都一样，A/B 毫无意义 |
| 13 | `/api/search` 的 `top_k` 直接当召回条数 | 召回仍取 `max(top_k, RETRIEVE_TOP_N)`，**返回只给 top_k 条** | 召回候选池要够大（融合质量），但前端要看几条就该给几条 —— 传 3 回 50 条是 bug |

### 8.3 还没做的

- **PDF OCR**：扫描件只标记 `needs_ocr`，不做识别。
- **会话历史**：`session_id` 字段留着，v1 不持久化。
- **`/api/eval/run`**：规划里的这个 GET 接口没实现，评测走命令行 `python -m app.eval.run`。
- **BM25 稀疏向量（SPLADE）**：§6 风险表里的备选方案，暂不需要。
